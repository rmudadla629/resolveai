# ResolveAI

An order support application with a Python API and browser interface. Responses are grounded in fictional store records, with a source reference for successful lookups.

## Current capabilities

- Look up shipped, processing, and delivered sample orders.
- Display readable responses through an accessible, responsive order lookup form.
- Handle missing and unknown IDs without inventing order details.
- Provide a JSON API for future tool integrations.
- Interpret natural-language order status questions using local Qwen3 4B through Ollama, then validate and execute a read-only order lookup.

AI question routing uses schema-constrained model output. Order IDs must appear in the original request; order facts are rendered directly from records rather than generated by the model. Missing or ambiguous IDs request clarification. Model errors are surfaced without pretending an AI response succeeded. The separate order ID form works without Ollama.

A manual cancellation review sandbox is implemented. There is no customer authentication; use only fictional data on localhost. The standard-library HTTP server is intended for local development. Model classification can still be wrong and requires broader evaluation before real use.

## Local AI setup

Install [Ollama](https://ollama.com/download/mac), keep it running, and download the model:

```sh
ollama pull qwen3:4b
```

The application calls only `http://127.0.0.1:11434/api/chat`, with thinking disabled, a 90-second timeout, and a bounded context. No API key is needed. Ask “Where is my order DEMO-1001?” in the question form. Each request is independent; conversation memory is not implemented. The model classifies intent and extracts an ID; Python controls the lookup and response. This is a constrained workflow, not an autonomous multi-agent system.

## Quick start

Requires Python 3.12. No external packages or API keys are needed.

```sh
python3 -m venv .venv
.venv/bin/python -m resolveai
```

Open http://127.0.0.1:8000/ and enter `DEMO-1001`, `DEMO-1002`, or `DEMO-1003`. Try `DEMO-9999` to check the unknown-order response. Stop the service with Control-C. Restart the service after changing code.

## API

| Endpoint | Purpose |
| --- | --- |
| `GET /` | Order lookup interface |
| `GET /api/order-status?order_id=DEMO-1001` | JSON order response |
| `GET /health` | Service health |
| `POST /ask` | Process a natural-language question and render its response |

The order API returns HTTP 200 for a match, 400 for a missing ID, and 404 for an unknown order. The browser form returns a page explaining the result.

## Architecture

Browser form → HTTP handler → order lookup tool → fictional JSON records.

Question form → local model intent/ID extraction → application validation → order lookup → record-based response.

- `resolveai/interface.py`: HTML rendering and escaped output.
- `resolveai/__main__.py`: localhost server and request routing.
- `resolveai/orders.py`: order retrieval and grounded response construction.
- `resolveai/agent.py`: local model request, structured decision validation, and lookup routing.
- `data/orders.json`: fictional sample records.
- `tests/test_orders.py`: behavioral and HTTP integration checks.

## Validation

```sh
.venv/bin/python -m unittest discover -s tests -v
```

Twenty-four tests cover order statuses, input normalization, missing and unknown IDs, HTML escaping, HTTP form/API responses, invented model IDs, unsupported requests, input limits, model failures, and evaluation scoring. Automated model tests use mocks; these verify application behavior rather than model accuracy.

## Live model evaluation

Keep Ollama running and execute:

```sh
.venv/bin/python -m resolveai.evaluate
```

The runner checks 18 labeled development scenarios in `data/eval_questions.json`: known and unknown orders, lowercase IDs, missing and multiple IDs, unsupported actions, unrelated questions, and an instruction override attempt. It checks structured outcomes, HTTP status, record identity/status, and source references. It reports pass rate, mean latency, p95 latency, and each response in a timestamped JSON file under `reports/`. Any failed case produces a nonzero exit code. No paid API is used.

This is a small development benchmark with one run per case. It is not a held-out accuracy estimate or proof of general safety. Generated-response quality is not measured because final order facts use fixed templates. Larger independent test sets and repeated runs are needed before making broader reliability claims.

## Policy retrieval

General policy questions are routed by the local model to a keyword retriever over three fictional policy sections in `data/policies.json`. Relevant passages are shown verbatim with links to `/policies` and stable section anchors. Questions with no matching keywords receive a missing-policy response. Policy excerpts describe general rules and do not establish eligibility for a specific order.

This is extractive policy retrieval, not embedding-based semantic search or generated RAG answers. Paraphrases without matching keywords may fail. Citation checks verify exact source text and document links. The live dataset includes six policy scenarios alongside the original twelve scenarios.

## Cancellation review sandbox

Open `/reviews` to submit a processing demo order (such as `DEMO-1002`) for review. Submission does not change the order. Approve or reject the pending request using the review buttons. Approval rechecks eligibility and changes only the fictional order status to `cancelled`; rejection leaves it unchanged. Shipped, delivered, unknown, and already cancelled orders are blocked. Pending requests are deduplicated and decisions cannot be applied twice.

SQLite transactions persist requests, status overrides, and audit events under ignored `runtime/reviews.sqlite3`. JSON order fixtures remain unchanged. Audit timestamps are UTC; no reviewer identity is recorded. The page includes a form token to reject blind cross-site submissions, but there is no login or role separation. Anyone with local app access can review requests. Keep the service on localhost; this is not production authorization or real order integration. AI chat does not submit or approve requests; use the explicit form.

Live model evaluations use isolated order fixtures so manual cancellations do not affect benchmark results. The tests use temporary databases and do not change the local sandbox.
