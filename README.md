# ResolveAI

An order support application with a Python API and browser interface. Responses are grounded in fictional store records, with a source reference for successful lookups.

## Current capabilities

- Look up shipped, processing, and delivered sample orders.
- Display readable responses through an accessible, responsive order lookup form.
- Handle missing and unknown IDs without inventing order details.
- Provide a JSON API for future tool integrations.
- Interpret natural-language order status questions using local Qwen3 4B through Ollama, then validate and execute a read-only order lookup.

AI question routing uses schema-constrained model output. Order IDs must appear in the original request; order facts are rendered directly from records rather than generated by the model. Missing or ambiguous IDs request clarification. Model errors are surfaced without pretending an AI response succeeded. The separate order ID form works without Ollama.

A manual cancellation review sandbox is implemented. Customer sign-in and fixed fictional ownership checks protect order access; use only fictional data on localhost. The Flask application is served by Waitress with localhost defaults. Model classification can still be wrong and requires broader evaluation before real use.

## Local AI setup

Install [Ollama](https://ollama.com/download/mac), keep it running, and download the model:

```sh
ollama pull qwen3:4b
```

The question router calls `http://127.0.0.1:11434/api/chat`, with thinking disabled, a 90-second timeout, and a bounded context. No API key is needed. Ask “Where is my order DEMO-1001?” in the question form. Each request is independent; conversation memory is not implemented. The model classifies intent and extracts an ID; Python controls the lookup and response. This is a constrained workflow, not an autonomous multi-agent system.

## Quick start

For an isolated local container setup, see [Container guide](CONTAINERS.md). Its build/start verification runs in GitHub Actions; full Compose inference needs a separate local test.

See [Demo guide](DEMO.md) for first-time setup, a five-minute walkthrough, troubleshooting, and a confirmed reset that preserves account credentials.

Requires Python 3.12. Install the pinned application dependencies; no API keys are needed.

```sh
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python -m resolveai
```

Open http://127.0.0.1:8000/ and enter `DEMO-1001`, `DEMO-1002`, or `DEMO-1003`. Try `DEMO-9999` to check the unknown-order response. Stop the service with Control-C. Restart the service after changing code.

## API

| Endpoint | Purpose |
| --- | --- |
| `GET /` | Order lookup interface |
| `GET /api/order-status?order_id=DEMO-1001` | JSON order response |
| `GET /health` | Service health |
| `POST /ask` | Process a natural-language question and render its response |

The order API returns HTTP 200 for a match, 400 for a missing ID, and 404 for an unknown order. The browser form returns a page explaining the result.

## Architecture

See [Architecture](ARCHITECTURE.md) for the system diagram and design choices, and [Project review](PROJECT_REVIEW.md) for measured results, known failures, and delivery gates.

Browser form → HTTP handler → order lookup tool → fictional JSON records.

Question form → local model intent/ID extraction → application validation → order lookup → record-based response.

- `resolveai/interface.py`: HTML rendering and escaped output.
- `resolveai/__main__.py`: configured Waitress startup.
- `resolveai/web.py`: Flask request dispatch, ownership checks, and error responses.
- `resolveai/orders.py`: order retrieval and grounded response construction.
- `resolveai/agent.py`: local model request, structured decision validation, and lookup routing.
- `data/orders.json`: fictional sample records.
- `tests/test_orders.py`: behavioral and HTTP integration checks.

## Validation

```sh
.venv/bin/python -m unittest discover -s tests -v
```

Fifty-four tests cover order statuses, input normalization, missing and unknown IDs, HTML escaping, HTTP form/API responses, invented model IDs, unsupported requests, input limits, model failures, and evaluation scoring. Automated model tests use mocks; these verify application behavior rather than model accuracy.

## Live model evaluation

Keep Ollama running and execute:

```sh
.venv/bin/python -m resolveai.evaluate
```

The runner checks 18 labeled development scenarios in `data/eval_questions.json`: known and unknown orders, lowercase IDs, missing and multiple IDs, unsupported actions, unrelated questions, and an instruction override attempt. It checks structured outcomes, HTTP status, record identity/status, and source references. It reports pass rate, mean latency, p95 latency, and each response in a timestamped JSON file under `reports/`. Any failed case produces a nonzero exit code. No paid API is used.

This is a small development benchmark with one run per case. It is not a held-out accuracy estimate or proof of general safety. Generated-response quality is not measured because final order facts use fixed templates. Larger independent test sets and repeated runs are needed before making broader reliability claims.

## Policy retrieval

General policy questions are routed by the local model to keyword-first retrieval over three fictional policy sections in `data/policies.json`. If no keywords match, `all-minilm:22m` embeddings rank sections by cosine similarity. The top section must score at least 0.35 and exceed the second by 0.06; otherwise retrieval abstains. These are development thresholds, not calibrated confidence probabilities. Keyword matches take priority and can still select irrelevant passages. If embeddings fail, the response explicitly identifies `keyword_fallback`.

Install the additional local embedding model:

```sh
ollama pull all-minilm:22m
```

Exact passages are shown with links to `/policies` and stable section anchors. The page displays the search method. Document embeddings are cached in memory by document content; edited policies get new vectors. No vector database is needed for three sections. This remains extractive retrieval, not generated answer synthesis. Policy excerpts describe general rules and do not establish eligibility for an individual order.

Compare retrieval independently of chat routing:

```sh
.venv/bin/python -m resolveai.compare_retrieval
```

The first local run scored keyword retrieval 5/10 and keyword-first semantic fallback 9/10 on `data/retrieval_questions.json`. Both methods missed “The product is faulty. What should I do?” The small set informed implementation and is not held out. Reports under `reports/retrieval-*.json` include each result, timings, model name, and dataset hash. This comparison does not measure end-to-end AI intent routing. Embedding failures cause the comparison to exit rather than misreport fallback as semantic performance.

## Cancellation review sandbox

Open `/reviews` to submit a processing demo order (such as `DEMO-1002`) for review. Submission does not change the order. Approve or reject the pending request using the review buttons. Approval rechecks eligibility and changes only the fictional order status to `cancelled`; rejection leaves it unchanged. Shipped, delivered, unknown, and already cancelled orders are blocked. Pending requests are deduplicated and decisions cannot be applied twice.

SQLite transactions persist requests, status overrides, and audit events under ignored `runtime/reviews.sqlite3`. JSON order fixtures remain unchanged. Audit timestamps are UTC; new events record alex, sam, or the single reviewer identity. Older events are marked legacy. The page includes a form token to reject blind cross-site submissions, and reviewer sign-in is required; customer order access is separately authenticated. Review controls require the configured local reviewer password. Keep the service on localhost; this is not production authorization or real order integration. AI chat does not submit or approve requests; use the explicit form.

Live model evaluations use isolated order fixtures so manual cancellations do not affect benchmark results. The tests use temporary databases and do not change the local sandbox.

## Continuous integration

The `Tests` GitHub Actions workflow runs the regression suite on pushes and pull requests using Python 3.12 on Ubuntu. It can also be started manually from the repository's Actions tab. The workflow uses mocked model responses; it does not install Ollama or run the live model benchmark. No API keys are required. Order and agent tests isolate their database so local cancellations cannot change their expected results.

## Local request tracing

AI question submissions through `/ask` receive a unique trace ID and record metadata in ignored `runtime/traces.sqlite3`. Open `/traces` or follow the response link to inspect the latest 100 requests and summary metrics over up to 1,000 retained records. Stored fields are trace ID, UTC timestamp, HTTP status, outcome, tool, retrieval method, and processing duration. Prompts, order IDs, response text, and exception text are not stored in this trace database. HTTP access logs and browser history are separate from tracing.

Duration includes routing and retrieval, but not form parsing, rendering, or network delivery. Metrics count HTTP 5xx as server/model errors; they do not measure answer accuracy, token usage, or cost. Direct order forms, review actions, and command-line evaluations are not included. Trace storage failure leaves the response usable and displays a warning. Unexpected processing exceptions return a generic error and record an internal-error outcome when storage is available.

This is local request-level instrumentation, not distributed tracing or model-level spans. The trace page has no sign-in; keep the service on localhost.

## Local reviewer sign-in

Create the reviewer password once, using a separate terminal tab:

```sh
.venv/bin/python -m resolveai.auth
```

Enter and confirm a password of at least 12 characters. Input is hidden. A salted PBKDF2 hash is stored in ignored `runtime/reviewer.json`; the plaintext password is not stored. The setup command refuses to overwrite an existing account. No password reset flow is implemented yet.

Restart ResolveAI, open `/reviews`, and sign in. Reviewer sessions expire after one hour, are invalidated at server restart, and can be ended with Sign out. Cookies use HttpOnly and SameSite=Strict. Secure cookies/TLS, password recovery, multiple reviewers, and deployment validation remain delivery gates; local login attempt limits are implemented. This authentication is for localhost only. The trace page remains unauthenticated; order lookup requires customer sign-in.

## Customer accounts and ownership

Configure fictional customer credentials with the local command:

```sh
.venv/bin/python -m resolveai.customers
```

Choose `alex` or `sam`, enter and confirm a password of at least 12 characters. Run again for the other account. Password hashes are stored in ignored `runtime/customers.json`; there is no web registration, password reset, or account replacement flow. Customer sessions use a separate cookie from reviewer sessions, expire after one hour, and end on logout or server restart.

Open `/account` to sign in. Alex owns DEMO-1001 and DEMO-1002; Sam owns DEMO-1003. Ownership is a server-side fictional mapping, not user-submitted data. Order pages, the JSON endpoint, AI order questions, and customer cancellation submissions enforce it. Inaccessible and unknown orders receive the same message. Signed-out users cannot retrieve order records; general policy questions remain public. Customer cancellation submissions create pending review only; customers cannot access reviewer decisions. Reviewer sign-in alone does not grant customer order access through the public lookup routes.

The local command-line workflows/evaluations use fixture-level access and are not customer-facing APIs. The 18-case live evaluation continues to use isolated fixtures, while HTTP permission tests cover customer ownership. No real identities or personal information are needed.

Already-cancelled DEMO-1002 remains cancelled; setup does not reset sandbox state. The reviewer may still submit test requests from the reviewer page. Existing audit records are preserved with actor `legacy`; new reviewer decisions use actor `reviewer`.

## Application server and configuration

`python -m resolveai` starts Waitress serving the Flask WSGI app, with debug mode disabled. It defaults to 127.0.0.1:8000 and four worker threads. Set `RESOLVEAI_PORT` (1–65535), `RESOLVEAI_THREADS` (1–32), or `RESOLVEAI_HOST` in the shell before launching to override defaults. Changing environment variables requires a restart; `.env` files are not loaded automatically.

The app and server limit request bodies to 8 KiB. Responses prevent browser caching and include frame denial and MIME-sniffing protections. Unexpected route errors return a generic 500 without exposing exception details. `/health` checks the HTTP application only, not Ollama or database readiness. CI installs `requirements.txt` before testing. Tests include a real Waitress HTTP smoke check.

Keep the localhost default. A deployment-ready server alone does not establish public readiness: HTTPS/Secure cookies, shared deployment rate limiting, deployment secrets/configuration, durable session storage, and operational validation remain unfinished. Sessions and the form token are process-local; use one process and expect sign-in again after restarting. Models still run through local Ollama. No hosting was created or purchased.

## Login attempt limits

Reviewer (`POST /login`) and customer (`POST /customer/login`) sign-ins each allow five attempts per connection IP in a fixed 60-second window. The sixth attempt returns HTTP 429 with a Retry-After header and retry guidance before checking a password. Successful, failed, and invalid-token submissions count; success does not reset the counter. Requests recover automatically when the window ends. No password or username is retained by the limiter.

Limits are role-endpoint/IP based rather than account based: switching customer usernames does not bypass the limit, while reviewer and customer windows are separate. Multiple people sharing an IP share that endpoint's budget. The local thread-safe store is bounded to 4,096 active keys. When full, new keys are temporarily blocked until a window expires; active limits are not evicted. Forwarded IP headers are not trusted. Logout, order lookup, policy questions, and health checks are not limited by this feature.

Counters are in memory, clear on server restart, and apply only to one process. Public deployments need a trusted proxy/IP policy and shared limits across processes. These controls do not establish protection against distributed attacks or denial of service. Local automated tests use simulated time to verify blocking and recovery without making the user wait.

## Container packaging

`Dockerfile` packages Flask/Waitress as a non-root application. `compose.yaml` publishes the app on localhost port 8001, uses private service networking for Ollama, and persists runtime state, reports, and model files in named volumes. The build context excludes local credentials and databases. `RESOLVEAI_OLLAMA_URL` supports the internal model service without changing the native localhost default.

The CI container job validates Compose, builds the image, runs regression tests inside it, and checks server health without downloading models. Full Compose inference and native ARM container execution require separate verification. Docker was not installed locally when this packaging was prepared. See [Container guide](CONTAINERS.md) for setup and verification limits.
